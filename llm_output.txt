# 1. Ten highest-risk areas

| # | Risk area | Why it is risky | QA focus |
|---|---|---|---|
| 1 | **Kafka duplicate delivery and out-of-order events** | Kafka can deliver the same event multiple times and events can arrive out of order. If consumers are not idempotent, side effects such as ERP export can happen twice. | Event idempotency, consumer retry, replay, partition failure, out-of-order handling. |
| 2 | **ERP export idempotency and partial success** | The ERP is an external system. A request may be accepted but the response may be lost. Retries can create duplicate ERP transactions if the idempotency key is unstable or missing. | Stable idempotency key, retry behavior, reconciliation, ERP mock testing. |
| 3 | **Expense state machine consistency and auditability** | Expenses move through states such as SUBMITTED, APPROVED, REJECTED, EXPORTED. Concurrent updates can corrupt state. Every transition must be auditable. | State transition tests, optimistic locking, audit logs, trace IDs. |
| 4 | **Approval authorization and two-level approval** | Expenses above $5,000 require two-level approval. Employees cannot approve their own expenses. Rejected expenses cannot be approved. Violations create financial and compliance risk. | Role-based authorization, approval workflow, API and UI enforcement. |
| 5 | **Duplicate expense detection** | Duplicate expenses must be detected. OCR errors, repeated uploads, or race conditions can allow duplicates to pass validation. | Duplicate detection rules, normalized matching, concurrency tests. |
| 6 | **OCR accuracy and exchange-rate correctness** | OCR is approximately 95% accurate. Amount, date, vendor, and tax extraction errors can cause incorrect financial records. Exchange rate must be applied by transaction date. | OCR golden-file tests, manual correction workflow, exchange-rate tests. |
| 7 | **Receipt file security** | Receipt files must never be publicly accessible. Misconfigured S3-compatible storage, public URLs, or weak access control can expose sensitive documents. | File upload validation, object storage access control, signed URL tests, authorization tests. |
| 8 | **Authentication and authorization** | OAuth2 + JWT protects API access. Token expiry, role escalation, or missing authorization checks can allow unauthorized approvals or exports. | AuthN tests, JWT lifecycle, role-based access, API authorization. |
| 9 | **Performance under 10,000 concurrent users** | The system must handle high concurrency with a 30-second API timeout. Kafka, database, ERP, and search/cache components can become bottlenecks. | Load testing, latency percentiles, throughput, timeout behavior. |
| 10 | **Resilience/recovery and cross-system consistency** | ERP may be unavailable for hours, Kafka partitions can fail, consumers can crash, and retries can storm. Because database transactions cannot span Kafka and ERP, consistency must be achieved through idempotency, outbox patterns, and reconciliation. | Chaos testing, outage simulation, consumer crash, retry storm, recovery validation. |

# 2. End-to-end QA strategy

## 2.1 Overall approach

The QA strategy should be failure-mode driven, not happy-path driven. The highest-value tests should focus on:

- Duplicate side effects
- Out-of-order events
- Partial success
- Race conditions
- Recovery after failure
- Auditability
- Security
- Performance under load

Recommended test environment:

- Staging environment with real or mock services:
  - Spring Boot APIs
  - PostgreSQL
  - Kafka
  - Redis
  - Elasticsearch
  - S3-compatible object storage
  - Mock ERP
  - Email/Teams notification mocks
- Synthetic receipt files for OCR testing.
- Trace IDs for every request, event, and state transition.
- A chaos harness for Kafka, ERP, database, and consumer failures.
- An ERP mock that can simulate:
  - Accepted request with lost response
  - Timeout
  - 500
  - 429
  - Partial response
  - Outage
  - Duplicate idempotency behavior

# 3. Investigation of the duplicate ERP export defect

The reported defect is:

> An expense was exported twice to the ERP even though the application showed only one EXPORTED record.

This strongly suggests a failure in end-to-end idempotency, especially around Kafka delivery, ERP retry, database state updates, or ERP-side deduplication.

Below are six technically plausible root causes.

---

## Root cause 1: Kafka duplicate delivery plus non-idempotent consumer

### How it could happen

The `ExpenseApproved` event is delivered twice to the export consumer. The consumer processes both events and calls the ERP twice. If the consumer does not check an idempotency key or database state before calling the ERP, the ERP receives two exports.

### How to reproduce

1. Create an expense.
2. Approve it.
3. Publish the same `ExpenseApproved` event twice with the same event ID and expense ID.
4. Run the export consumer.
5. Observe that the ERP mock receives two export requests.

### Logs/metrics/traces to inspect

- Kafka event ID
- Kafka offset
- Kafka partition
- Consumer group
- Consumer lag
- ERP request log
- ERP idempotency key
- ERP external transaction IDs
- Database status update log
- Trace ID

### Regression test

Test that duplicate delivery of the same approved event results in exactly one ERP export and one EXPORTED state transition.

---

## Root cause 2: Export retry after timeout with unstable idempotency key

### How it could happen

The export service calls the ERP. The ERP accepts the request, but the response is lost or times out. The export service retries. If the retry uses a new request UUID or no stable idempotency key, the ERP may treat it as a new transaction and export the expense twice.

### How to reproduce

1. Mock ERP accepts the first request but returns a timeout or no response.
2. Export service retries with a new or unstable idempotency key.
3. ERP accepts the second request.
4. ERP records two external transactions.
5. Application may show only one EXPORTED record if it stores only the last external ID.

### Logs/metrics/traces to inspect

- HTTP status code
- Timeout duration
- Retry count
- Idempotency key
- ERP external transaction IDs
- ERP request timestamps
- Database status update
- Trace ID

### Regression test

Test that a retry after timeout uses the same stable idempotency key and the ERP returns the same external transaction ID without creating a second transaction.

---

## Root cause 3: Race condition in database state update

### How it could happen

Two consumer threads or processes read the expense status as not exported. Both call the ERP before either updates the database status to EXPORTED. The database does not use row locking, optimistic concurrency, or a unique export constraint, so both side effects occur.

### How to reproduce

1. Create an approved expense.
2. Start two export workers processing the same event.
3. Both read status as not exported.
4. Both call ERP.
5. Both update database status.
6. ERP receives two exports.

### Logs/metrics/traces to inspect

- Database row version
- Lock wait time
- Worker/thread ID
- ERP request log
- Status update timestamp
- Trace ID
- Consumer offset

### Regression test

Test concurrent processing of the same approved event and assert that only one ERP export occurs. Use row locking, optimistic locking, or a unique idempotency constraint.

---

## Root cause 4: Upstream duplicate approval event publication

### How it could happen

The approval API publishes the `ExpenseApproved` event twice. This can happen because:

- A manager clicks approve twice.
- The API retries after a timeout.
- The producer sends the event twice due to network retry.
- The approval endpoint is not idempotent.

The consumer then receives two approved events and exports twice.

### How to reproduce

1. Call the approve endpoint twice for the same expense.
2. Observe two `ExpenseApproved` events in Kafka.
3. Run the export consumer.
4. Observe two ERP exports.

### Logs/metrics/traces to inspect

- API request log
- Approval endpoint idempotency behavior
- Kafka event publish count
- Event ID
- Kafka offset
- ERP request log

### Regression test

Test that the approval API is idempotent and that duplicate approval attempts produce only one approved event and one ERP export.

---

## Root cause 5: Consumer crash after ERP call but before database commit

### How it could happen

The consumer calls the ERP and receives an external transaction ID. Before the consumer updates the database status to EXPORTED, it crashes. The Kafka offset is not committed. On restart, the consumer replays the event and calls the ERP again.

### How to reproduce

1. Consumer processes approved event.
2. ERP call succeeds.
3. Consumer crashes before database update.
4. Consumer restarts.
5. Event is replayed.
6. ERP receives a second export.

### Logs/metrics/traces to inspect

- Consumer crash log
- Kafka offset commit status
- ERP request log
- Database status update log
- External transaction IDs
- Trace ID

### Regression test

Test consumer crash recovery and replay. Assert that replay does not create a second ERP export. Use idempotency key, transactional outbox, or ERP-side deduplication.

---

## Root cause 6: Stale cache or out-of-order status read

### How it could happen

The export consumer reads a stale Redis cache value indicating the expense is not exported. The database may already have been updated, but the cache is not consistent. A duplicate event is processed using the stale cache value, causing a second ERP export.

### How to reproduce

1. Expense status is updated to EXPORTED in database.
2. Redis cache still says not exported.
3. Duplicate event is processed.
4. Consumer uses stale cache.
5. ERP export happens again.

### Logs/metrics/traces to inspect

- Redis cache read/write log
- Database status
- Event order
- Cache invalidation timestamp
- ERP request log
- Trace ID

### Regression test

Test cache consistency and stale reads. Assert that the database is the source of truth and stale cache values do not cause duplicate ERP exports.

# 6. Idempotency test design for ERP export

## 6.1 Recommended idempotency key

Use a stable business-level idempotency key, not a per-request UUID.

Recommended key:

```text
expenseId + ":" + approvedEventId
```

If the system guarantees one export per expense, a simpler key may be:

```text
expenseId
```

However, using `expenseId + approvedEventId` is safer if approval events can be replayed or versioned.

## 6.2 Request generation

Example ERP request:

```json
{
  "idempotencyKey": "EXP-1001:APR-2001",
  "expenseId": "EXP-1001",
  "amount": 1234.56,
  "currency": "USD",
  "transactionDate": "2025-01-15",
  "vendor": "Vendor A",
  "tax": 100.00
}
```

The idempotency key must remain the same across retries.

## 6.3 Retry behavior

On timeout, 500, 429, or network failure:

- Retry with the same idempotency key.
- Use exponential backoff.
- Add jitter.
- Limit retry attempts.
- Use circuit breaker if ERP is unavailable.
- Do not generate a new idempotency key per retry.

## 6.4 Database state

Before ERP call:

- Expense status should be `APPROVED` or `EXPORT_PENDING`.
- Export record should have a unique idempotency key.
- Database should prevent duplicate export records.

After ERP success:

- Expense status becomes `EXPORTED`.
- External transaction ID is stored.
- Audit log records the transition.

If ERP response is partial:

- Expense should not become `EXPORTED` until external transaction ID is confirmed.
- A reconciliation job should verify ERP state.

## 6.5 Expected ERP behavior

First request:

- ERP creates one external transaction.
- ERP returns external transaction ID.

Duplicate request with same idempotency key:

- ERP does not create a second transaction.
- ERP returns the same external transaction ID.
- ERP may return 200 or 201 with the same ID, depending on API design.

## 6.6 Assertions

The test should assert:

1. ERP mock created transaction count = 1.
2. ERP external transaction ID count = 1.
3. Database export record count = 1.
4. Expense status is `EXPORTED` exactly once.
5. Audit log contains exactly one `EXPORTED` transition.
6. If response is lost, reconciliation finds the existing external transaction ID.
7. No duplicate external transaction IDs exist.

## 6.7 Recommended architecture comparison

Option A: Client-side idempotency only  
- Pros: Simple.
- Cons: Fails if ERP accepts request but response is lost.

Option B: ERP-side idempotency only  
- Pros: Strong external deduplication.
- Cons: Depends on ERP API design and ERP reliability.

Option C: Client-side + ERP-side + transactional outbox  
- Pros: Strongest protection.
- Cons: More complex.

Recommended: Use a transactional outbox pattern plus stable idempotency key plus ERP-side deduplication.

The outbox pattern helps because database transactions cannot span Kafka and ERP. The database transaction writes the expense state and an outbox event. A relay publishes the outbox event to Kafka. The consumer processes it idempotently. The ERP call uses a stable idempotency key.

# 7. Race conditions in approval/export workflow

At least five race conditions are possible.

## 7.1 Two managers approve the same expense concurrently

Two managers read the expense as SUBMITTED and both attempt approval. Without row locking or optimistic concurrency, both may create approval records or publish duplicate approved events.

Prevention:

- Row lock or optimistic locking
- Unique approval constraint
- Idempotent approval API
- Event deduplication

---

## 7.2 Approval and rejection happen concurrently

One manager approves while another rejects. Without state locking, the system may allow an invalid transition or create conflicting audit records.

Prevention:

- State machine validation
- Row lock
- Version check
- Audit log with conflict detection

---

## 7.3 Export consumer and ERP reconciliation update concurrently

The export consumer updates the expense status while a reconciliation job also updates the external transaction ID. Without concurrency control, one update can overwrite the other.

Prevention:

- Optimistic locking
- Unique export key
- Single source of truth
- Idempotent update

---

## 7.4 Duplicate expense submission race

Two users submit the same expense at the same time. Duplicate detection may check the database after both inserts, allowing both to pass.

Prevention:

- Unique constraint on normalized expense fields
- Row lock during duplicate check
- Idempotent submission API
- Post-insert duplicate detection

---

## 7.5 OCR correction and approval race

OCR extracts amount, date, vendor, and tax. If OCR correction happens after approval, the approved amount may be stale. If approval uses stale OCR data, the exported amount may be wrong.

Prevention:

- Versioned expense data
- Approval validation against latest OCR data
- Audit log for OCR corrections
- Re-validation before export

---

## 7.6 Stale cache and database state race

UI or consumer reads a stale Redis cache value while the database has already changed. This can cause duplicate approvals, duplicate exports, or incorrect status display.

Prevention:

- Database as source of truth
- Cache invalidation
- Versioned cache keys
- Consistency checks

---

# 11. Automation pseudocode for detecting duplicate ERP export

Below is Java-style pseudocode for a test that detects duplicate ERP export caused by duplicate Kafka delivery.

```java
@Test
void duplicateApprovedEventShouldProduceOneErpExport() {
    // 1. Create expense
    Expense expense = expenseService.createExpense(
        "EXP-1001",
        1234.56,
        "USD",
        "2025-01-15",
        "Vendor A",
        100.00
    );

    // 2. Approve expense
    expenseService.approve(expense.getId(), "manager-1");

    // 3. Build stable idempotency key
    String eventId = "APR-2001";
    String idempotencyKey = expense.getId() + ":" + eventId;

    // 4. Publish duplicate approved event
    ExpenseApprovedEvent payload = new ExpenseApprovedEvent(
        expense.getId(),
        eventId,
        idempotencyKey,
        expense.getAmount(),
        expense.getCurrency(),
        expense.getTransactionDate(),
        expense.getVendor(),
        expense.getTax()
    );

    kafkaProducer.send("expense.approved", expense.getId(), eventId, payload);
    kafkaProducer.send("expense.approved", expense.getId(), eventId, payload);

    // 5. Start consumer
    exportConsumer.start();

    // 6. Wait for processing
    awaitConsumerProcessed(eventId);

    // 7. Assert ERP received only one export
    List<ErpCall> erpCalls = erpMock.getCalls();
    assertThat(erpCalls.size()).isEqualTo(1);

    // 8. Assert ERP created only one external transaction
    List<String> externalIds = erpCalls.stream()
        .map(ErpCall::getExternalTransactionId)
        .toList();
    assertThat(new HashSet<>(externalIds).size()).isEqualTo(1);

    // 9. Assert database status is EXPORTED once
    Expense dbExpense = expenseRepository.findById(expense.getId());
    assertThat(dbExpense.getStatus()).isEqualTo(ExpenseStatus.EXPORTED);
    assertThat(dbExpense.getExternalTransactionId()).isNotNull();

    // 10. Assert export record exists once
    assertThat(exportRepository.countByExpenseId(expense.getId())).isEqualTo(1);

    // 11. Assert audit log records one EXPORTED transition
    assertThat(auditRepository.countTransitions(
        expense.getId(),
        ExpenseStatus.EXPORTED
    )).isEqualTo(1);
}
```

A supporting mock ERP could be:

```java
class MockErp {
    private final Map<String, String> externalIds = new HashMap<>();

    ErpResponse export(ErpRequest request) {
        String key = request.getIdempotencyKey();

        if (externalIds.containsKey(key)) {
            return new ErpResponse(externalIds.get(key));
        }

        String externalId = "ERP-" + UUID.randomUUID();
        externalIds.put(key, externalId);
        return new ErpResponse(externalId);
    }

    List<ErpCall> getCalls() {
        return callLog;
    }
}
```

This test detects the reported defect by asserting that duplicate Kafka delivery does not produce duplicate ERP exports.

# 12. Challenge the QA strategy: five assumptions and failure modes

## Assumption 1: ERP can enforce idempotency using a stable key

### Assumption

The ERP API can accept a stable idempotency key and return the same external transaction ID for duplicate requests.

### What could go wrong if false

If the ERP does not support idempotency or uses a per-request identifier, retries after timeout or network failure can create duplicate ERP transactions. The application may still show only one EXPORTED record, but the ERP will have two.

Mitigation:

- Require ERP-side deduplication.
- Use reconciliation jobs.
- Store all external transaction IDs.
- Alert on multiple external IDs for one expense.
- Manually reconcile duplicates.

---

## Assumption 2: Kafka consumer can be made idempotent using event ID and database constraints

### Assumption

The consumer can safely process duplicate events by checking event ID, expense ID, and database state.

### What could go wrong if false

If the consumer performs side effects before checking database state, or if database constraints are missing, duplicate events can still cause duplicate ERP exports.

Mitigation:

- Use transactional outbox.
- Use row locking or optimistic concurrency.
- Use unique export idempotency key.
- Validate state before side effect.
- Test crash recovery and replay.

---

## Assumption 3: OCR accuracy of 95% is acceptable with manual correction

### Assumption

OCR errors can be detected and corrected by users or managers.

### What could go wrong if false

If OCR errors are not caught, incorrect amount, date, vendor, or tax values can be approved and exported. Financial records may be wrong.

Mitigation:

- Use golden-file OCR accuracy tests.
- Require manual review for high-value expenses.
- Validate amount/date/vendor/tax before approval.
- Audit OCR corrections.
- Reconcile exported amounts with ERP records.

---

## Assumption 4: Three QA engineers can cover the required risk-based regression in two weeks

### Assumption

The team can build and maintain enough automation to cover P0/P1 risks within the release cycle.

### What could go wrong if false

If automation is insufficient, P0/P1 risks may escape to production. Duplicate ERP export, state corruption, or security issues may occur.

Mitigation:

- Shift testing left.
- Automate P0 tests.
- Use nightly chaos and integration tests.
- Prioritize defect investigation.
- Accept documented risk only for P2/P3.
- Add production monitoring and alerting.

---

## Assumption 5: Zero-downtime deployment and data migration are safe

### Assumption

Deployment and migration can occur without downtime and without corrupting expense state, Kafka events, or ERP exports.

### What could go wrong if false

A failed migration or deployment can leave expenses in inconsistent states, duplicate events in Kafka, or ERP exports out of sync with database status.

Mitigation:

- Test rollback.
- Use canary deployment.
- Validate data migration.
- Reconcile Kafka and ERP after deployment.
- Feature-flag risky changes.
- Monitor audit trail after deployment.
